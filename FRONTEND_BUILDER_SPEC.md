# Frontend Builder Specification - Project Health Reporting Agent

Build only the functionality described here. Do not add mock data, demo-only flows, placeholder buttons, static fake dashboards, or frontend pages for backend capabilities that do not exist.

## Product Goal

Create a clean executive-facing frontend for the Project Health Reporting Agent. The app helps Professional Services leadership upload project plan Excel files, run backend RAG analysis, review project health evidence, download weekly reports, and generate a monthly executive presentation.

The frontend must be data-driven. Every visible metric, chart, report, table row, RAG color, recommendation, and download link must come from the backend or from files generated by the backend.

## Current Backend Status

The backend is implemented and verified as a Python package.

Working backend capabilities:

- Read `.xlsx` project plans.
- Parse multi-sheet workbooks.
- Preserve all task-sheet attributes in SQLite.
- Normalize project, task, comment, summary, schedule, milestone, baseline, variance, float, critical, and status fields.
- Reconstruct WBS hierarchy from `Level` and `Ancestors`.
- Derive RAG status independently from deterministic weighted signals.
- Store explainability audit records in SQLite.
- Generate weekly Markdown reports.
- Generate weekly JSON reports.
- Generate a monthly PowerPoint executive deck.
- Run a simple natural-language SQLite query command.
- Run tests through pytest.

Current backend storage:

- SQLite database: `storage/project_health.sqlite` or any path passed by the caller.
- Weekly outputs: `outputs/weekly/`
- Monthly outputs: `outputs/monthly/`

Current backend commands:

```powershell
.venv\Scripts\python -m project_health.cli analyze --input data/input --output outputs --db storage/project_health.sqlite
.venv\Scripts\python -m project_health.cli synthesize --db storage/project_health.sqlite --output outputs/monthly
.venv\Scripts\python -m project_health.cli ask --db storage/project_health.sqlite "Which projects have external dependency blockers?"
.venv\Scripts\python -m pytest -q
```

## API Key Requirement

No API key is required for the current backend.

The current reasoning layer is deterministic/offline and does not call OpenAI, Claude, or any other LLM provider. If LLM-based reasoning is added later, API keys may be placed in `.env`, but the frontend must not require or request API keys.

## Strict Frontend Rules

The frontend builder must follow these rules:

- Do not create mock projects.
- Do not create fake RAG counts.
- Do not create fake trend lines.
- Do not create fake charts.
- Do not create fake comments or stakeholder sentiment.
- Do not create fake budget values.
- Do not create fake upload success states.
- Do not create placeholder buttons.
- Do not create login, roles, admin settings, notifications, or integrations unless backend endpoints exist.
- Do not show a budget panel unless the backend returns budget data.
- Do not show trend charts unless the backend returns at least two snapshots for the relevant project or portfolio.
- Do not allow editing RAG weights unless a backend update endpoint exists.
- Do not invent backend fields. Use only the response fields defined in this spec.

If data is unavailable, show an honest empty state such as:

- "No project snapshots available yet. Upload project plans and run analysis."
- "No stakeholder comments were found in this workbook."
- "Budget data is unavailable in the uploaded project plan."
- "Trend view requires at least two weekly snapshots."

## Required Frontend Pages

### 1. Upload And Analyze

Purpose:

Allow the user to upload one or more Excel project plans and trigger backend analysis.

Required UI:

- File picker accepting `.xlsx` only.
- List of selected files before submission.
- Primary action: `Run Analysis`.
- Loading state while analysis runs.
- Success state showing analyzed projects returned by backend.
- Error state showing backend error message.

Do not:

- Pretend analysis succeeded before backend response.
- Display reports until backend returns generated report paths.
- Add drag-and-drop animations if they obscure the basic upload flow.

Backend mapping:

- This maps to the existing backend `analyze` capability.
- A thin integration API can wrap `project_health.cli.run_analyze`.

Expected integration endpoint:

```http
POST /api/analyze
Content-Type: multipart/form-data
```

Request:

- `files`: one or more `.xlsx` files.
- Optional `run_date`: `YYYY-MM-DD`.

Response:

```json
{
  "run_date": "2026-07-08",
  "snapshots": [
    {
      "snapshot_id": 1,
      "project_id": 1,
      "project_name": "Zycus - UniSan S2P Implementation",
      "rag_status": "Red",
      "rag_score": 77.7,
      "confidence": "Medium",
      "data_quality_score": 68.5,
      "weekly_markdown_path": "outputs/weekly/project.md",
      "weekly_json_path": "outputs/weekly/project.json"
    }
  ]
}
```

## Visual Design Requirements

The UI should feel like an executive project health tool:

- Clean, professional, dense enough for scanning.
- Avoid marketing landing-page design.
- Avoid oversized hero sections.
- Use restrained colors.
- RAG colors:
  - Red: high-risk
  - Amber: watch-list
  - Green: healthy
- Use tables for evidence.
- Use compact cards only for real metrics.
- Use clear empty states.
- Use loading states for backend calls.
- Use error states that show backend error messages.

## Data Handling Requirements

- All dates must display in readable format.
- Preserve source row numbers wherever task evidence is shown.
- Show `source_schedule_health` separately from agent-derived `rag_status`.
- Show data quality score prominently.
- Show budget as unavailable unless backend explicitly returns budget fields.
- Show stakeholder sentiment as unavailable when comments are absent.
- Never calculate RAG in the frontend.
- Never calculate signal weights in the frontend.
- Never mutate report JSON in the frontend.

## Backend Integration Notes For Codex

When the frontend folder is returned, integrate it by adding a thin backend API wrapper around the existing Python functions and SQLite queries.

Existing Python functions to wrap:

- `project_health.cli.run_analyze`
- `project_health.cli.run_synthesize`
- `project_health.repositories.fetch_portfolio`
- `project_health.repositories.fetch_snapshots`
- `project_health.repositories.fetch_top_risk_tasks`
- `project_health.repositories.simple_query`
- SQLite queries for snapshot detail, tasks, comments, signals, and generated files.

Do not duplicate RAG scoring logic in the frontend or API layer. The scoring source of truth is:

- `src/project_health/rag_engine.py`
- `config/rag_weights.json`
- SQLite table `rag_signals`

The frontend is acceptable only if:

- It can upload real `.xlsx` files.
- It can trigger backend analysis.
- It displays only backend-returned projects.
- It displays only backend-returned RAG values.
- It displays signal evidence from backend data.
- It can download generated weekly reports.
